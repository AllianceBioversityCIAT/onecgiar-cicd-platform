# Architecture Change 03 — Generic remote-script CD (technology-neutral contract)

| Field | Value |
|---|---|
| Status | **Decision adopted by the owner (2026-10-08).** Spec update in this document, design §6.1, §6.3, §6.5, DD-26 and requirements FR-03, FR-13, FR-22; tasks §6.0.4 (G-1…G-5). Implementation local only; no AWS, GitHub or server change |
| Owner intent | ONECGIAR CI/CD Platform replaces Jenkins progressively for many platforms and environments. Each platform and environment has its own CI (GitHub Actions) and its own deploy script installed on its server. **The Executor does not deploy applications: it safely runs authorized remote scripts.** No deploy technology (Docker, ECR, PM2, Tomcat, Java, Node.js…) is a requirement of the Executor |
| Supersedes | Any reading of AC-02 V1 or design §6.5 that makes Docker, ECR, image digests, units or `deploy-container.sh` universal requirements. AC-02 V1 is otherwise unchanged |
| Not changed | Origin authorization (OIDC, shared CI role, option A source binding), least privilege, strict host-key pinning, Secrets Manager for credentials, dedupe, supersede ordering, distributed lock with fencing, target mutex, deploy windows, closed state machine, audit, Slack, DEV-only scope of the deployed infrastructure (NFR-09). No security control is weakened |

## 1. Responsibilities

| Layer | Owns | Never does |
|---|---|---|
| **CI** (GitHub Actions, per platform and environment) | Build, tests, quality gates, packaging, artifact publication (Docker/ECR or anything else), promotion rules. Calls the common reusable workflow to request a deploy | Deploy logic, SSH, choosing a host or script |
| **Common CD request** (reusable workflow `deploy-request.reusable.yml`) | OIDC with the shared CI role, the source binding (session name = `repository_id`), building and pushing container images **only when units are given**, sending exactly one `DEPLOY_REQUESTED` | Application build steps of a platform (those stay in the caller's own jobs) |
| **Executor** (generic) | Receive, authorize the sender and the source repository, validate the target, deploy windows, dedupe and ordering, distributed lock and fencing, execution state, SSH with the pinned host key and the referenced credential, run the target's authorized script with the contract arguments, interpret the exit code and `CICD_RESULT`, record the requested vs verified version, audit and notify | Docker, PM2, Tomcat or any platform command; container names, ports, health checks, migrations, rollback, image pruning, downloading or installing artifacts, building, interpreting Jenkins instructions, expressions or argument templates |
| **Deploy script** (per platform and environment, on the target) | Knowing its application and environment, obtaining or receiving the version, dependencies, the procedure, application checks, rollback when it supports it, protecting its shared resources, returning the common result | Trusting anything but its own admin-owned configuration and the contract arguments |

## 2. Decisions

| # | Decision |
|---|---|
| G-D1 | **Argument mode per target.** The target record has an optional `scriptArguments`: `standard` (default when absent, so every existing record keeps today's behavior) or `none`. `none`: the Executor runs `<deployScript>` with **no** argument. `standard`: the Executor runs `<deployScript>` with the contract vector (G-D2). There are no per-target argument templates, no expression evaluation and no interpolation: the request can never add, remove or shape an argument, and the script path always comes from the registry |
| G-D2 | **Standard vector, technology-neutral:** `--target-id <id> --execution-id <id> --fencing-token <n> --commit-sha <40-hex>` followed by one `--artifact <name>=sha256:<64-hex>` per requested artifact (sorted by name; none when the request carries none). Every value is validated by the request schema or generated by the Executor and shell-quoted by the transport. A script may use any subset and ignore the rest; a script MAY still reject what it does not expect (the Docker reference script does) |
| G-D3 | **Artifacts are optional immutable content references** (supersedes the "images only" reading of DD-26). `artifacts` in the request is optional (0–8 entries); each value is a `sha256:<64-hex>` content digest of whatever the CI produced (a container image, an archive, a WAR…), named by a component. A request without artifacts identifies its version by `commitSha` alone |
| G-D4 | **Common CD request mechanism.** The reusable workflow stays the only producer of `DEPLOY_REQUESTED`. Its Docker build and push become optional (`units` may be `[]`) and the caller may pass already computed immutable references (`artifacts` input, validated like the request schema; names disjoint from the units and units + artifacts at most 8, the schema's limit). The caller's own jobs do the platform build. Pinning the new workflow commit in the CI role trust is an **external change pending owner authorization** (stack parameter `PinnedWorkflowSha`) |
| G-D5 | **Technology-neutral exit-code contract** (codes unchanged, meaning generalized; §3) |
| G-D6 | **`CICD_RESULT` stays the common result**: only `status` is required; `deployedImages` is a generic map component → deployed reference (any technology); a new optional `deployedCommit` (40-hex) reports the commit actually deployed. Missing `CICD_RESULT` never fails a run but is flagged |
| G-D7 | **Request processed ≠ script succeeded ≠ version verified.** On a successful run the Executor records `versionCheck` = `VERIFIED`, `MISMATCH` or `NOT_REPORTED` and `versionGuaranteed` (`false` in `none` mode) on the execution, and notifies it (§4). A `MISMATCH` does not change the closed state machine (the script did succeed) but is recorded and notified for operator attention |
| G-D8 | **Shared servers.** Different targets on the same server may run in parallel (the Executor's lock is per target). Resources shared by several targets are protected by the scripts (§5); the Executor never models them |
| G-D9 | `deploy-container.sh` is the **Docker specialization** of the contract (standard mode, artifacts = image digests), not the universal mechanism. Its known pruning limitation (shared ECR repository) must be fixed before two Docker targets share a server |

## 3. Common result contract (every script)

| Exit | Neutral meaning | Executor outcome | Historical label |
|---|---|---|---|
| 0 | Deployed (or already at the requested version) | `SUCCEEDED`; `lastDeployed` written with fencing; version check (§4) | — |
| 10 | Failed **before any change** to the running service (fetch, download, prepare, validation) | `FAILED` (code `PULL`) | `PULL` |
| 20 | Failed in a **pre-switch step** (for example a migration); the running service was not stopped | `FAILED` (code `MIGRATION`) | `MIGRATION` |
| 30 | Failed **switching** to the new version and the script **confirms** the previous state was restored | `FAILED` (code `START`) | `START` |
| 40 | Failed **verification** after switching and the script **confirms** the previous state was restored | `FAILED` (code `HEALTH`) | `HEALTH` |
| 50 | Target busy: the target mutex is held; **nothing was done** | Lock retry (X14) | `TARGET_BUSY` |
| any other code (1, 2, 126, 127…), a timeout or a lost session | Unknown: the service may be changed and not restored | `UNKNOWN_TARGET_STATE` (operator review, runbook §12.2) | — |

- A script that cannot restore (no rollback support) MUST NOT exit 30 or 40 after changing the service: it exits with a code outside the table, so the state is reported unknown, never as restored.
- **Mapping scripts derived from Jenkins stages.** A Jenkins-style script fails with `exit 1` (or `set -e`). Wrapped as is, every failure would be `UNKNOWN_TARGET_STATE`. Generated scripts use the template (`deploy-scripts/templates/deploy-script-template.sh`): each phase runs under a trap that maps a failure before the switch to 10 (or 20 for a pre-switch step), a failure after the switch to 30/40 only when the restore command succeeded, and anything else to an unknown code.
- The script MUST take the target mutex before any effect and return 50 without effects when it is held (FR-11, DD-22).
- Last stdout line on 0/10/20/30/40/50: `CICD_RESULT {"status":…, "deployedImages":{…}?, "previousImages":{…}?, "deployedCommit":"<40-hex>"?, "migrations":"APPLIED|NONE|FAILED"?, "healthy":bool?, "mutexHolder":"…"?}`.

## 4. Version traceability

| Property | `standard` | `none` |
|---|---|---|
| Requested version recorded | Yes: `commitSha`, `artifacts`, run metadata on the execution | Yes (same) |
| Script receives the version | Yes (`--commit-sha`, `--artifact`) | **No.** The script decides what it deploys |
| Deployed version known | When `CICD_RESULT` reports it | Only if `CICD_RESULT` reports it |
| No other version deployed by accident | When the script uses the received references | **Not guaranteed** (`versionGuaranteed: false`) |
| Obsolete requests never overwrite newer ones | Executor: supersede ordering, `highestDispatched`, lock with fencing | Executor ordering still applies to dispatch, but the script's own source may be newer or different |

**Verification rule (`versionCheck`, on exit 0 only):**
- `MISMATCH` when `CICD_RESULT.deployedCommit` is present and differs from the requested `commitSha`, or when the request carried artifacts, `deployedImages` is present and a requested digest appears in none of its values.
- `VERIFIED` when there is no mismatch and either `deployedCommit` equals the requested commit, or the request carried artifacts and every requested digest appears in `deployedImages` (a value equal to the digest or ending with `@<digest>`).
- `NOT_REPORTED` otherwise (no `CICD_RESULT`, or no comparable field).
- `none` mode: the same rule applies to whatever the script reports, and `versionGuaranteed` is always `false`; a `VERIFIED` there means "the script reported the requested version", not "the platform enforced it".

**`lastDeployed` is the ordering record, not the verified version.** For every successful run it records the request's ordering value and commit (supersede protection depends on it), also after a `MISMATCH` or in `none` mode; there it may differ from what is actually running. `TARGET.currentImages` reflects only what the script reported, and `versionCheck` on the execution says whether the requested version was proven.

`none` is therefore restricted: use it only for scripts whose deploy source is fixed outside the request (for example a human-promoted package), set `deployWindowPolicy: required` where Jenkins still deploys the same service, and never present its version as confirmed unless `versionCheck` is `VERIFIED`.

## 5. Shared servers and concurrency

| Case | Who protects |
|---|---|
| Same target, two requests | Executor: distributed lock by `targetId` with fencing, `highestDispatched`; script: target mutex (exit 50) |
| Different targets, independent resources | Nobody needs to: they may run in parallel (bounded by `CICD_SSH_CONCURRENCY`) |
| Different targets sharing a resource (Docker daemon pruning, one Tomcat, a port, a directory, a reverse proxy, a configuration file, a system service) | **The scripts:** every script touching the shared resource takes the same additional local lock (for example `flock /var/lock/cicd/resource-<name>.lock`) and keeps its own effects scoped; or the platforms are modeled as **one target** so the Executor serializes them |
| Jenkins still deploying during the transition | Per target: `deployWindowPolicy: required`, the window opened only after the Jenkins jobs are disabled; and the script's local locks also guard against manual runs |

The Executor never assumes two targets are independent: it simply does not serialize different targets. Declaring shared resources is part of onboarding (runbook 09 checklist).

## 6. Pending external changes (not done here)

- New commit of `deploy-request.reusable.yml` (optional units, `artifacts` input) → `PinnedWorkflowSha` stack update and caller re-pin: **owner authorization required**. Until then, the deployed trust keeps the R-8 commit, which supports the Docker flow unchanged.
- No IAM, registry, secret or server change is required by G-D1…G-D9.
